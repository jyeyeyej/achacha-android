## 재실행

프로젝트 루트에서 다음 중 하나를 실행한다.

```powershell
npm run test:api
```

```powershell
node scripts/test-bus-apis.mjs
```

스크립트는 다음 순서로 검증한다.

1. 루트 `.env`를 읽고 `DATA_GO_KR_SERVICE_KEY` 존재 여부를 확인한다.
2. 서울 정류장을 검색하고 정류장 상세에서 현재 노선 ID를 얻는다.
3. 서울 노선 전체 도착정보에서 첫째·둘째 차량이 있는 정류장을 확인한다.
4. 경기 정류장을 검색하고 검색된 정류장의 도착정보를 조회한다.
5. 네 API의 인증 성공과 첫째·둘째 차량 제공 여부를 요약 출력한다.

## 보안 검토

### 로컬 PC 테스트

- `.env`와 `.env.*`는 `.gitignore` 대상이다.
- 공유 가능한 예시 파일은 `.env.example`뿐이며 실제 키는 포함하지 않는다.
- 테스트 스크립트는 키, 키가 포함된 URL, 원본 응답 전문을 출력하지 않는다.
- 인코딩 키가 입력돼도 내부에서 한 번 디코딩한 뒤 URL 인코딩해 이중 인코딩을 피한다.

### Android APK 직접 연동 위험

`BuildConfig`, 리소스, 문자열 상수 또는 네이티브 라이브러리에 키를 넣어도 APK를 분석하면 복구할 수 있다. 난독화는 키를 비밀로 만들지 못한다.

서울 버스 API 호스트는 검증 시 HTTPS 443 연결에 실패하고 공식 문서대로 HTTP 80만 사용할 수 있었다. Android가 서울 API를 직접 호출하면 다음 위험이 있다.

- 인증키와 요청 파라미터가 암호화되지 않은 전송 구간에 노출될 수 있음
- 응답이 중간자 공격으로 변조될 수 있음
- Android의 기본 cleartext 차단을 풀어야 하며 보안 수준이 낮아짐

### 권장 연동 방식

Android 앱이 공공 API를 직접 호출하지 않고 최소 HTTPS 중계 서버를 사용한다.

```text
Android 앱 ── HTTPS ──> 아차차 중계 서버 ──> 서울/경기 공공 API
```

중계 서버는 다음 범위로 제한한다.

- 공공데이터 인증키를 서버 환경변수/비밀 저장소에만 보관
- 허용된 네 API와 정해진 파라미터만 전달
- 요청 URL과 예외 로그에서 `serviceKey` 제거
- 사용자·IP별 호출 제한 적용
- 짧은 캐시를 사용해 동일 조회 중복 호출 감소
- 서울 HTTP 응답을 서버에서 받은 뒤 앱에는 HTTPS로 전달
- 서울·경기 응답을 공통 JSON 모델로 정규화

개인용 APK라도 서울 API가 HTTP 전용인 현재 상태에서는 중계 서버 방식을 우선 권장한다. 서버 없이 진행할 경우 키 노출과 전송구간 위험을 수용해야 하며, 키 폐기·재발급과 호출량 모니터링 절차가 필요하다.
